# Terraform Azure Portfolio Project

A demo project provisioning Azure infrastructure with Terraform, using HCP Terraform for remote state and run execution. Built to demonstrate secrets/config hygiene alongside working infrastructure code — nothing sensitive is committed to this repo.

## Status

- [x] Resource group config written
- [x] HCP Terraform org + workspace created (CLI-driven)
- [x] Local `terraform init` working
- [ ] Remote plan execution — blocked on service principal auth (in progress)
- [ ] Additional resources (VNET, storage account, etc.)

## Prerequisites

Install these locally before working on this repo:

- **Terraform CLI** (1.15.0 or later) — [download](https://developer.hashicorp.com/terraform/install). Check your version with `terraform version`.
- **Azure CLI** — needed for `az login` and creating the service principal. Check with `az version`.
- **VS Code** with the HashiCorp Terraform extension (for formatting/linting `.tf` files).
- **An HCP Terraform account** with an organization created (this project uses org `CRTesting`).
- **An Azure subscription** to deploy into.

## Repo structure and what's gitignored

This repo is set up so anyone can clone it and understand the shape of the project, without any real credentials, org names, or resource values being exposed.

**Committed to git:**
- `main.tf`, `variables.tf` etc. — the actual Terraform config
- `.gitignore`
- `.terraform.lock.hcl` — pins exact provider versions, safe and useful to share
- `terraform.tfvars.example` — placeholder variable values, shows what's needed
- `set-env.ps1.example` — placeholder env var script, shows what's needed

**Gitignored (local only, never pushed):**
- `.terraform/` — provider plugins and module cache, regenerated by `terraform init`
- `terraform.tfvars` — your actual variable values (e.g. resource group name, location)
- `set-env.ps1` — your actual HCP org/workspace names
- `*.tfstate*` — not actually used here since state lives remotely in HCP, but ignored as a safety net
- `.env`

The `.example` files exist so the real workflow is documented without exposing real values — copy them and strip the `.example` suffix, then fill in your own details.

## Setting environment variables

Two environment variables are required locally, so Terraform knows which HCP org/workspace to talk to. These can't be set as normal Terraform variables, since the `cloud {}` block is evaluated before variables are resolved.

Create `set-env.ps1` (gitignored) in the repo root:

```powershell
$env:TF_CLOUD_ORGANIZATION="CRTesting"
$env:TF_WORKSPACE="demo-workspace"
```

Run it at the start of each VS Code terminal session (it doesn't persist once the terminal closes):

```powershell
.\set-env.ps1
```

Confirm it worked:

```powershell
echo $env:TF_CLOUD_ORGANIZATION
echo $env:TF_WORKSPACE
```

## Authenticating to HCP Terraform

One-time step, persists across sessions (stored under your Windows user profile, not in the repo):

```powershell
terraform login
```

Follow the browser prompt to generate a token and paste it back into the terminal.

## Authenticating to Azure

Local `terraform init` and CLI-based checks use your logged-in Azure CLI session:

```powershell
az login
az account show
```

Check `az account show` prints the subscription you actually want to deploy into — `az login` can pick the wrong one if your account has access to more than one subscription.

**Note:** `az login` only covers local runs. HCP Terraform's CLI-driven workflow executes `plan`/`apply` remotely on HCP's own Linux runners by default, which have no access to your local Azure CLI session. Remote runs need a service principal instead (below).

## Service principal (for remote plan/apply via HCP)

1. Create the service principal, scoped to your subscription:

   ```powershell
   az ad sp create-for-rbac --name "terraform-portfolio" --role="Contributor" --scopes="/subscriptions/YOUR_SUBSCRIPTION_ID"
   ```

   This outputs `appId`, `password`, and `tenant` — keep these safe, `password` is only shown once.

2. In the HCP Terraform UI, go to the workspace → **Variables** → add as **environment variables**, marking the secret ones **Sensitive**:

   | Variable | Value | Sensitive? |
   |---|---|---|
   | `ARM_CLIENT_ID` | the `appId` | No |
   | `ARM_CLIENT_SECRET` | the `password` | Yes |
   | `ARM_SUBSCRIPTION_ID` | your subscription ID | No |
   | `ARM_TENANT_ID` | the `tenant` | No |

   These live only in HCP's UI, never in this repo.

## Provider version note

`azurerm` provider is pinned with `~>` to allow patch/minor updates. From v5.0 onward, the provider no longer auto-registers Azure Resource Providers by default — this only matters once resources beyond `azurerm_resource_group` are added (e.g. `Microsoft.Network` for a VNET). Not an issue yet.

## Destroying resources

To avoid ongoing charges while experimenting:

```powershell
terraform destroy
```

HCP workspace and state persist after a destroy — only the actual Azure resources are torn down, so the project can be rebuilt without redoing the HCP setup.
